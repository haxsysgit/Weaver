# Plan 033.5: Meaning search keeps up

> **Executor instructions:** Give search's meaning half every chapter on
> the shelf, and keep it current: add the chapters it has never seen,
> re-embed the ones that changed on disk, and do it again after every
> weekly refresh. Then run the twelve Reader Experience Trials on the
> finished build. The rule that governs it: the index is extended in
> place with exactly the settings it was built with (proved by matching
> stored vectors), never deleted and rebuilt.

Planning-agent findings this plan rests on (measured 2026-11-04, no model
spend; confirmed by admission):

- The live index (6,826 chunks, chapters 1 to 3127) was built with the
  story chunker at **40 target lines, 19 overlap**. Re-chunking with those
  settings reproduces the stored line spans for all 3,046 chapters whose
  text is unchanged, and re-embedding on CPU reproduces stored vectors at
  cosine 1.000 (chapters 1, 2000, 3000).
- **81 chapters (3047 to 3127) changed on disk after they were indexed**
  (their stored source hash no longer matches), so their stored line spans
  can point at the wrong lines today. They are re-embedded too.
- Chapters 3128 to 3232 (105) were never embedded.
- `build_library_index` defaults to 12 and 5 and a ceiling of 1000, so
  running the build script today would build a different index from the
  live one. Point ids come from Python's `hash()`, which changes per
  process, so a re-run would duplicate points instead of replacing them.

## Scope

- **Update in place.** One library function and one command that bring
  the index level with the shelf: for each chapter on the shelf, compare
  its current source hash with the hash stored in the index; chapters
  missing or changed have their old points removed (by chapter) and new
  points written with the pinned settings (40 and 19, `bge-large-en-v1.5`
  dense, BM42 sparse, the same payload fields), with point ids that are
  stable across processes. Unchanged chapters are not touched or
  embedded. A second run changes nothing.
- **Coverage.** `coverage.json` records the highest chapter N such that
  every chapter 1 to N is current in the index, so the prompt's reach
  line stays true.
- **Pinned settings.** The chunk settings and models live in one place,
  used by the update and by `scripts/build_library_index.py`, whose
  ceiling defaults to the shelf, not 1000.
- **Command.** `weaver library index` brings the index up to date;
  `weaver library index --check` reports what it would do (chapters
  missing, changed, current; coverage) and writes nothing.
- **Weekly refresh.** After its chapter step, the scheduled refresh runs
  the same update (also when no chapter was added but the index lags). If
  the index is busy (the server is running), it records that the index is
  waiting and how far it reaches, does not fail the refresh, and catches
  up on the next run.
- **The real run** on the owner's machine, then the twelve Reader
  Experience Trials on the finished build.

## Out of scope

- Re-chunking to fit the model's 512-token window (helped vectors alone,
  not the blend; Plan 033 learning). A GPU path.
- Notebook statements past chapter 1000 in the index (a separate question
  for Plan 034's notebook work).
- Any change to how search ranks, the prompt rule, or the answer path.
  Trial failures go to a follow-up plan (Plan 033 review finding 10).
- Settings UI. The status file gains fields; Settings is unchanged.
- Merge, tag, deploy.

## Deterministic proof / verification floor

1. Backend: `uv run pytest -q` passes (865 passed, 4 skipped at the 033
   close, plus the new tests). Ruff clean on changed files.
2. Frontend unchanged; `npx vitest run`, `npx tsc`, `npm run build` still
   pass.
3. Tests with a fake embedder prove: a new chapter is added; a changed
   chapter's old points are gone and new ones written; an unchanged
   chapter is not embedded; a second run writes nothing; point ids are the
   same in two processes; coverage stops below the first missing or stale
   chapter; `--check` writes nothing; a busy index gives a clear waiting
   status in the scheduled refresh, not a failure.
4. Match test before the real write: the pinned settings reproduce stored
   line spans and vectors (cosine at least 0.999) for at least three
   unchanged chapters across the novel.
5. After the real run: `--check` reports 0 missing, 0 changed, coverage
   equal to the shelf's last chapter; point count recorded; a search limited
   to chapters 3128 to 3232 returns hits found by meaning; a search on an
   old chapter returns the same top hits as before the run.

## STOP conditions

- The match test fails (spans differ or cosine below 0.999 on an
  unchanged chapter): stop before writing; report.
- Any step would delete or recreate the whole collection.
- The full floor fails twice on the same cause.
- Live spend would pass $2.70 (cap $3.00).
- A Reader Trial fails: record it and carry on to the next trial; no
  prompt or code change inside this plan.
- Anything under `novels/` would be written.
